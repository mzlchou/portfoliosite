RISC-V RV32I Processor
RTL to GDSII

A 32-bit RISC-V RV32I processor designed in SystemVerilog and taken through the complete ASIC design flow — from RTL and functional verification, through synthesis, to a fully placed-and-routed layout on a 16 nm PDK.

  • View on GitHub

Overview

This project, built for a graduate digital IC design course, implements the base integer subset of the RISC-V instruction set (RV32I) as a single-cycle processor and carries it end to end through a modern ASIC flow. The goal was less about microarchitectural performance and more about experiencing the full path a real chip takes: register-transfer-level (RTL) design, functional verification, logic synthesis, and the complete physical implementation flow down to a GDSII layout. The design was implemented on a 16 nm process design kit using industry-standard Cadence tools, with the flow automated through TCL and Makefiles. It was a five-person team effort (Connor Bremner, Weston Nguyen, Devon Kumar, Brian Liau, and myself); my contributions centered on the arithmetic logic unit, the AHB bus interface work, and the physical-implementation flow.

Architecture

The core is a non-pipelined, single-cycle datapath: every instruction completes in one clock cycle, flowing combinationally from instruction fetch through decode, register read, execute, memory access, and write-back. Only the program counter, register file, and data memory update on the clock edge. The design is built from small, independently verified SystemVerilog modules:

  • Program Counter — increments by four or loads a branch/jump target computed by the ALU.
  • Instruction Decoder — a purely combinational control unit that extracts register fields and generates every control signal, exploiting the RV32I encoding so the funct3 field maps directly onto the ALU operation.
  • Immediate Generator — reassembles and sign-extends immediates across all six RISC-V instruction formats.
  • Register File — 32 × 32-bit registers with two combinational read ports and a synchronous write port, with x0 hardwired to zero.
  • Arithmetic Logic Unit — eight operations (add/sub, shifts, comparisons, and bitwise logic) reused for arithmetic, address calculation, and branch-target computation.
  • Load/Store Unit — drives memory control signals and performs byte/halfword/word extraction with correct signed and unsigned sign extension.

A deliberate design choice was to reuse the single ALU for all addition — data-path arithmetic, memory address calculation, and PC-relative branch/jump targets — with operand multiplexers selecting between the program counter, register values, the zero register, and immediates.

Verification

Correctness was established bottom-up. Each module was first validated in isolation with its own self-checking testbench, then the integrated processor was exercised with full instruction sequences at the system level. Verification used C++ testbenches compiled and simulated through Verilator, giving fast, cycle-accurate simulation. Proving each block correct before integration kept later debugging focused on wiring and interaction rather than block-level logic.

RTL-to-GDSII Flow

Once functionally verified, the design was synthesized into a gate-level netlist with Cadence Genus and then physically implemented with Cadence Innovus. The backend flow covered the complete sequence of physical-design stages:

  • Floorplanning — defining the core area, margins, and standard-cell rows.
  • Power planning — building a hierarchical VDD/VSS power mesh across the metal stack to deliver current with minimal IR drop.
  • Placement — legalizing every standard cell into rows with timing- and wirelength-driven optimization.
  • Clock tree synthesis — constructing a balanced buffer tree so the clock reaches all sequential elements with minimal skew, followed by hold-time fixing.
  • Routing — connecting all signals across the metal layers within the design rules, with no routing congestion.
  • Signoff — final timing, design-rule, and parasitic checks on the routed layout before GDSII export.

Timing was verified across multiple corners (multi-mode multi-corner analysis), checking setup at the slow corner and hold at the fast corner. The flow closed with positive setup and hold slack and zero timing violations.

Results

Process / PDK 16 nm
Target frequency 50 MHz (20 ns period)
Total area 21,496 µm² 23,652 µm²
Total power 1.33 mW 2.21 mW
Timing Positive setup & hold slack — no violations

The area is dominated by memory: the data memory was implemented as a register array rather than a compiled SRAM macro, so the bulk of the ~9,200 flip-flops in the design are memory storage. This made the layout memory-dominated and the utilization intentionally low — a useful, concrete illustration of how an architectural choice (flop-based memory versus an SRAM macro) propagates directly into area, power, and clock-tree size.

Bus Interface (AHB-Lite)

Alongside the directly-integrated design, I designed and simulated an AHB-Lite (AMBA) bus interface for a more realistic memory architecture, with the CPU acting as the bus master and instruction and data memory as separate slaves connected through an AHB interconnect. This required a master-side finite-state machine that bridges the single-cycle core to the bus's two-phase, wait-state protocol — stalling the core across the multi-cycle transaction and capturing read data the moment it becomes valid — and a subordinate wrapper that translates the AHB handshake into a simple enable/address/data interface for the memory.

Scope & Outcome

Initial goals also included pipelining, the RISC-V vector extension (RVV), and bus-based memory. As the project progressed, the vector hardware and the bus-connected memory introduced verification and physical-design complexity that put a clean signoff at risk within the project timeline. To guarantee a complete, verifiable end-to-end implementation, the final taped-out design was scoped to the non-pipelined RV32I core with directly-integrated memory; the AHB bus was designed and verified in simulation but not carried into the final physical build. The result is a functional RV32I processor implemented through the entire flow from RTL to GDSII, with the design trade-offs in area, power, and timing explored and documented along the way.
